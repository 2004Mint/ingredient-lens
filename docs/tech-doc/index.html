Chapter 01

项目概述

成分镜是一个“读成分表”的工具：把化妆品包装背面的成分表粘进来，十秒内给出 一句结论、三条理由、一把排位尺。结论由规则引擎判定，大模型只负责把结论讲成人话。

1.1问题：成分表是公开的，但没人看得懂

中国法规要求化妆品标签按加入量从高到低列出全部成分。也就是说，排位本身就是含量信息： 排在第 11 位之后的成分，通常只剩千分之几。这条规则是公开的，但消费者拿不到三个东西：

  • 排位的含义——“烟酰胺排第 3”到底算不算主打？前 5 位和后 10 位的差别有多大？
  • 和自己的关系——同一瓶东西，油皮、敏感肌、孕期看到的结论应该不一样，但标签上只有一个配方。
  • 可核对的说法——博主测评是二手解读，通用大模型会给出“浓度约 5%”“能治痘痘”这类无法核对、甚至越界的话。

1.2我们做了什么

三件事，对应三个层次：

① 结论层：规则引擎读完排位、成分角色、法规限量、你的档案，给出四档结论之一 —— 可以放心 / 需要留意 / 建议避开 / 信息不足。 这一层不经过模型，因此可复现、可测试、可追责。

② 解释层：模型把已经判定好的事实写成 2–4 句中文。 它不能新增成分、不能出现任何数字、不能出现医疗用语——三道闸门在它后面等着。

第三层是证据层：报告默认只展开结论和三条理由，完整清单、法规提示、成分详情折叠在后面。 用户不需要一次看完 30 个成分，他只需要知道“这瓶能不能用，为什么”。

1.3关键数字

90成分库当前条目（内置 60）
< 1s规则出结论
150单次解析成分上限
6AI 输出闸门

1.4边界：我们不做什么

不做原因
不给商品打分、不推荐买哪一瓶我们只读标签，不测评商品；打分需要配方外信息，也容易被当成广告
不替代皮肤科诊断、不给用药建议医疗建议有执业边界；模型输出里九个医疗用语一律拦截
不让模型判断限量与禁忌法规判断必须可追溯，交给规则表和人工维护的成分库
不把“没认出来”包装成“没问题”覆盖率低于 50% 时直接给“信息不足”，而不是给一个好看的绿灯
这条边界不是免责声明，而是产品设计的一部分。它决定了后面所有的技术取舍： 为什么结论必须由规则给、为什么模型不能碰数字、为什么认不出时要明说认不出。

3.4四个关键设计决策

决策选择代价与应对
ADR-1 结论由谁给规则引擎判定，模型只解释规则表要人工维护；换来可复现、可测试、可追责。测试见第 6 章
ADR-2 解释要不要流式流式，但必须可回退流式天然会断。用 finish_reason + 句末标点判定断流，再走非流式重试与模板兜底
ADR-3 数据怎么存单机 JSON，原子写不适合多用户并发；换来零运维、数据不出机、评委一条命令就能跑
ADR-4 要不要向量 RAG不做90 条结构化数据上向量库是过度工程；改用名称索引 + 排位权重 + 同义词表，结论可解释
关于 ADR-4 的取舍：评审表里 RAG 占 6%。我们评估后主动放弃，原因是成分库是小规模结构化数据， 向量召回带来的模糊匹配会污染风险判断（把“柠檬烯”召回到“柠檬酸”是灾难）。 我们用同义词表 + 中文二元组做检索，并把“为什么不用向量”写进文档 —— 这是一个有依据的工程判断，不是缺功能。
Chapter 04

AI 技术方案

这一章回答三个问题：为什么这样选型、怎么接进来、怎么让它不出错。 核心判断只有一句：让模型做它擅长的表达，不让它做它不擅长的判断。

4.1选型理由

4.1.1 为什么不用“把成分表丢给大模型”

这是最省事的做法，也是我们最先否掉的做法。端到端生成有四个致命问题：

问题具体表现我们的对策
会编造模型倾向补全“浓度约 5%”“添加量 0.1%”这类标签上没有的数字结论由规则给；输出层直接禁止任何数字
不可复现同一份成分表，两次回答的严重程度、措辞、甚至结论都可能不同结论层完全确定；解释层允许措辞变化，但不允许改变结论
无法核对“烟酰胺刺激性低”这类断言没有出处每条理由绑定成分库条目或排位，界面上可见依据标签
会越界顺口给出“可以治痘痘”“建议用处方药”九个医疗用语硬拦截；prompt 里同时禁止

4.1.2 那为什么还需要模型

规则能算出结论，但算不出语气。把“柠檬烯 排位 13、敏感肌高风险、香精 12、羟苯甲酯 有限量” 这堆结构化事实写成一段人话，让读者知道“先避开哪个、哪些只是留意”，是模型的强项 —— 尤其是把三四个并列事实压缩成有主次的因果句。这部分工作我们试过模板，读起来像机器播报； 试过拼接，句子之间没有逻辑连接。模型在这个位置是合适的。

分工边界：模型可以决定“先说哪个、怎么连接、用什么语气”；不能决定“严重程度、排位、是否限量、是否有风险”。 前者是表达，后者是事实。闸门就是这条边界的具体实现。

4.1.3 模型与接入方式

项选择理由
协议OpenAI 兼容的 Chat Completions国内主流服务商都兼容；换供应商只改三个配置项，不改代码
配置后台填写 base_url / model / key密钥不进仓库、不进前端；评委可用自己的 Key 复现
语言模型可配置，默认流式 + 600 max_tokens解释只有 2–4 句，600 足够；上限压低也降低了跑飞的概率
视觉模型独立配置，可关闭拍照识别是可选能力；没配就隐藏入口，不假装能用
无 Key 时整链路降级规则照跑，解释用本地模板，并明确标注“本地模板”而不是“AI 生成”

4.2集成方式

4.2.1 流式协议：四个事件

解释走 POST /api/explain/stream，返回 text/event-stream。 没有用 EventSource，因为需要 POST 带 JSON body 和中断控制，前端用 fetch + ReadableStream 自己解析。事件只有四类：

事件字段前端行为
stepkey / text / state渲染推理步骤条：读取规则结论 → 生成解释 → 数字与用语校验
deltatext追加到正文，光标跟随
replacetext / source / reason整段替换（重试成功或回退模板），并标注来源
donesource / reason收尾：llm 表示模型输出，template 表示本地模板

为什么要有 replace：流式的中间态是不可信的（可能只有半句）。我们的策略是——先让用户看到字在动， 同时在后台判断这段输出是否完整、是否违规；不完整就整段替换成重试结果，违规就整段替换成模板。 用户看到的是“解释晚了一秒”，而不是“一句被截断的话”。

4.2.2 Prompt 结构与上下文裁剪

System 只有四条硬性要求，越短越不容易被忽略：

1. 只能使用事实里出现的信息，不得新增成分，不得推测任何浓度或含量。
2. 禁止出现任何阿拉伯数字、百分号或「百分之」。
3. 不得给出医疗建议，不得使用「治疗」「诊断」「处方」「疗效」等词。
4. 不用 Markdown、不用列表、不加标题，直接输出句子；不要重复事实清单。

User 侧只放裁剪后的事实：结论等级、匹配到的成分与排位、命中的风险项（最多 3 条）、覆盖率。 不放全文成分表——放了模型就会逐条复述，既浪费 token，也更容易编造。 这是本方案在“上下文工程”上的主要取舍：给判断结果，不给原始物料。

4.3优化策略：四道工序把不确定性收回来

4.3.1 断流检测：不能把“半句话”当成成功

最早的做法是“收到第一个 delta 就算成功”，结果线上出现了以逗号结尾的句子。 现在的判定要求两个条件同时成立：

  • 上游返回的 finish_reason 是正常结束（stop），而不是空值或长度截断；
  • 输出以句末标点收尾：。！？… 或右引号、右括号。

任一不满足，就判定为“上游提前结束”，先走非流式重试一次（completeChat， 同样 600 max_tokens）；重试结果仍要过同样的判定与闸门；再不通过，就回退本地模板， 并把原因（“上游输出不完整”或缩短后的错误信息）显示在报告底部。

4.3.2 输出闸门：数字与医疗用语零容忍

检查规则不通过时
长度20 ≤ 字数 ≤ 520过短视为没说完，过长视为跑题
数字拦截阿拉伯数字、全角数字、「百分之」、中文数字 + %；成分名与代号里的数字（1,2-戊二醇、二苯酮-3、维生素B5、SPF50）先剥离再检查先尝试改写计数，改不了才回退模板
医疗用语治疗 / 治愈 / 诊断 / 处方 / 根治 / 疗效 / 药效 / 药用 / 医美回退模板，并点名违规词
断流finish_reason + 句末标点重试一次 → 仍失败则回退
“一个数字都不许有”是有代价的。模型不能说“10 秒”“1 个成分”，甚至不能说“第 11 位”。 为了让解释依然有信息量，我们改用相对表述：前段 / 中段 / 后段、靠前 / 靠后、多数 / 少数。 这个约束反过来塑造了文案风格 —— 也正因为如此，数字只能来自规则层，读者看到的每个数字都可核对。

这套闸门最早有一个自相矛盾的地方，是在真实调用里暴露出来的：上下文把「成分总数」「第几位」「限量 2.0%」 原样喂给模型，prompt 又禁止输出数字 —— 模型照抄事实，就必然被自己的闸门拦下，用户看到的是“解释里出现了具体数字，已改用规则说明”。 现在的做法是从源头掐断：

环节做法
事实层计数一律写成中文（「第十二位」），限量值换成「有明确的法规限量要求」，致痘性只给等级（低 / 较低 / 中等 / 较高 / 高）
闸门先把成分名里的数字（1,2-、-3）剥离再检查；含 % 直接拦，不给豁免
改写只差计数时，把「第 5 位」改写成「第五位」后重新校验，通过就保留模型原文，不退回模板
不改写带百分号或剂量单位（2.0%、0.5 克）一律不改写 —— 那是在说浓度，直接回退模板

改之前，模型写一句「5 个成分」就会被整段替换成模板；改后再跑同一份配方与成分详情，解释全部由模型生成、违规零次， 产品评测的输出护栏也 5/5 通过（记录见 docs/eval/评测记录-v1.md）。 回退时给用户看的是「本地解释：这次回答没写完」，不是内部术语。

4.3.3 兜底模板：宁可朴素，不要空白

模板按结论等级与风险项拼装，读起来不惊艳，但信息完整：先说要避开什么，再说需要留意什么， 最后给一句边界提醒。界面上会标注“本地模板生成”，不冒充 AI。 这样即使模型服务完全不可用，报告仍然是完整可用的 —— 这是“离线可用”的技术含义。

4.3.4 覆盖率先行：不够就不下结论

当前端视图层发现 matched / total < 0.5 且规则结论为“可以放心”时， 会把结论降级为“信息不足”，并把未识别的成分作为虚线占位保留在原排位（不跳号）。 这条规则的目的是：不要用一个漂亮的绿灯掩盖“我们没认出 10 个成分”这件事。

4.4Agent 工作流：研究 Agent 怎么自己决定下一步

未收录成分的处理不是「一次模型调用」，而是一个会自己决定「要不要调模型、要不要重试、能不能入库」的 Agent。 它只做一件窄事 —— 把一个没见过的成分查清楚 —— 但这件事天然需要计划、工具和判断。

4.4.1 计划：五步，写在代码里，也写在界面上

01
normalize归一化：去括号注释、去序号、全角转半角。「（日用）香精」→「香精」
02
search_library先查成分库（精确匹配）。命中就直接结束 —— 不花一次模型调用
03
ask_model按固定 Schema 让模型补全草稿：角色、作用、风险标签、限量、置信度
04
infer_role / validate角色缺失时用词根规则兜底（paraben→防腐、sulfate→表活）；然后校验字段
05
置信度标注≥ 0.7 记为高置信度；不够仍然收录，但标注低置信度并写明理由，管理等事后复核

4.4.2 自主决策：四个分支，都能被测试

观察到的结果Agent 的决定理由
成分库已有（精确命中）结束，不调用模型已知的东西不需要重新研究，也避免模型改写已有条目
字段不合法换一种写法再问一次（最多两次）括号写法常常是模型没认出来的原因，换回原始写法往往能补全

置信度 < 0.7仍然收录，但打上「低置信度」标记并留下理由不收录就永远认不出这个成分；收了才能让报告完整，人工随时可复核

4.4.3 轨迹：每一步都留痕

每次运行都会写一条 trace：第几步、调了哪个工具、参数是什么、观察到什么、耗时多少、成功还是失败。 管理台可以逐条展开，用户端只看到「正在研究哪几个成分」。下面这条是真实运行的记录 （模型 deepseek-v4.1-flash，输入一个虚构成分，模型自己决定先查了两次库）：

01 normalize　　　　假想成分XYZ测试 → 无需改动　ok　1 ms
02 search_library　 假想成分XYZ测试 → 库内未收录　miss　0 ms
03 tool_call　　　　模型请求工具（1632 ms 的思考后）　ok
04 tool:search_library　{"name":"假想成分XYZ测试"} → 未收录　ok　1 ms
05 tool_call　　　　模型再次请求工具　ok
06 tool:lookup_limit　{"name":"假想成分XYZ测试"} → 未收录　ok　0 ms
07 ask_model　　　　假想成分XYZ测试 → 草稿 · 置信度 0.12　ok　5308 ms
08 validate　　　　字段齐全，角色「功效」　ok　0 ms
→ 结论：置信度 0.12 低于阈值 0.70，仍会收录并标注低置信度（虚构成分，模型自己也没把握，管理台可据此拒绝）

4.4.4 自动收录：Agent 自己写库，但每一步都可追溯

Agent 字段校验通过后直接写入成分库，不需要人工点通过 —— 否则每遇到一个新成分，报告就会永远卡在 「还有成分没认出」。写入的条目标记为 source=ai、status=pending， 带置信度、模型名、依据原文与完整轨迹，管理台随时能复核、改字段或删除。

风险控制靠三件事，而不是靠人工闸门：只有字段合法的草稿才收录（名称/角色/作用缺一不可）； 低置信度会被标记并写明原因；冲突不硬写 —— 库里已有同名但不是括号变体时，这条任务记为失败， 不会覆盖已有条目。三条都由 ResearchCommitService 统一执行，自动收录与管理台手动通过走同一个入口。

4.4.5 工具调用与 MCP：让模型自己取证

上面五步里，第 3 步不是「一次性把事实塞给模型」，而是带工具的对话：模型可以先要求查一次库再作答。 暴露给它的三个工具都是只读的，参数与返回都受控（MCP 侧另有一个受令牌保护的写入口，见本节末尾）：

工具模型什么时候会调返回
search_library拿不准这个写法是不是库里已有成分的别名是否已收录、标准名、角色
lookup_limit要写「限量」字段之前先核对限量原文，或「没有限量记录」
list_role_examples拿不准该归到哪个角色该角色下的若干示例成分

Agent 执行工具后把观察结果作为 tool 消息回灌，再请模型继续；最多两轮， 防止模型在工具里绕圈。如果服务商不认 tools 字段（返回 400 且报错提到 tool/function）， 会自动去掉工具重试一次，并在轨迹里记下「退回确定性计划」—— 工具不被支持不应该让整条任务失败。

实测（2026-11-12，deepseek-v4.1-flash）：模型在一次真实运行里先调 search_library、 再调 lookup_limit，两次都拿到「未收录」之后才给出草稿，并把置信度压到 0.12。 这条轨迹同时证明了三件事：工具真的被模型主动调用、结果真的被回灌、没把握时会自己标注低置信度并留下理由。

同一套能力另外做成了一个 MCP Server（mcp/server.mjs，零依赖，stdio JSON-RPC）： 三个只读工具开放给任意 MCP 客户端，Claude Desktop / Cursor 配一行 JSON 即可接入；另有一个受令牌保护、带限流的 submit_research 写入口，让外部客户端也能把「没见过的成分」送进研究队列。 它和产品内 Agent 共用同一份成分库与同一条边界 —— 未收录时返回「不要编造」，而不是让模型自由发挥。

写入口是故意默认关着的：只有设置了 COSME_MCP_TOKEN 才可用，令牌不对返回 401， 同一进程 10 分钟内最多 10 次（超出返回 429）；提交进去的查询走的是与产品完全相同的 「入队 → Agent 研究 → 自动收录」链路。一个会烧模型额度的写接口，不应该默认对局域网开放。

为什么这算 Agent 而不是「一个函数」：它有自己的计划、会选工具、会根据观察结果改变下一步（命中就停、不合法就换写法、 没把握就交人），并且全过程可回放；工具既可以由模型临时决定调用，也可以由计划强制触发。 区别不在于用了多少模型，而在于决策是不是数据驱动的、过程是不是可见的。

4.5多模态：拍照识别与语音输入

01
用户主动拍照 / 选图未配置视觉模型时入口不显示
02
发给视觉模型要求只返回成分表文本，不解释、不补全
03
回到同一条解析链路识别结果进文本框，用户可改；后续与粘贴完全一致
04
失败降级识别不可用时提示改用粘贴，并保留“重试”“改用文本”两个动作

为什么不让视觉模型直接出结论：识别错误会一路传导致结论错误。把图像识别限制在“转写文本”这一步， 用户能看到并纠正中间结果——这比一个看不见的错误链条可靠得多。

语音是第二条输入通道：Web Speech API 把口述的成分表转成文本，同样回到这条解析链路； 报告页用 SpeechSynthesis 朗读结论。识别与朗读都在浏览器内完成，不上传音频，也不增加服务端成本； 浏览器不支持时入口直接隐藏，降级成粘贴——多模态是增强，不是前置条件。

4.8成本与用量控制

这类工具很容易在成本上失控：每看一瓶都调一次模型、每次解释都把完整成分表塞进上下文、 失败了反复重试。我们的做法是把调用量压在“必要且唯一”上：

控制点做法效果
调用次数一份报告只生成一次解释；切换档案会重新分析，但解释仍只请求一次不因滚动、展开、重渲染而重复调用
输入长度上下文只放结论、命中的风险项（≤3 条）、覆盖率，不放完整成分表输入 token 与成分数量解耦：150 个成分也不会把上下文撑爆
输出长度max_tokens 固定 600，prompt 要求 2–4 句输出上限可预期，也降低跑飞概率
重试策略断流时只做一次非流式重试，不再循环最坏情况两次调用后必定收敛到模板
按需深化成分详情的解释在点击时才请求不看详情就不产生费用
零成本路径未配置 Key 时不发起任何请求评委本地复现不需要任何额度

研究队列同理：只有出现未收录成分时才入队，入队后也不是无限重试，而是单次研究 + 自动收录 + 事后可追溯。 换句话说，模型花掉的每一分钱，都对应一次用户主动发起的、且不会重复的请求。

Chapter 05

核心功能实现

5.1输入：把真实世界的脏数据变干净

真实成分表的格式非常乱：顿号、中文逗号、英文逗号、换行、空格混用；带“1.”“①”序号； 带括号注释“（又名 XX）”；同一成分重复出现；还有把“水”写成“去离子水”的。 解析器做四件事：

  • 切分：按顿号、逗号、分号、换行、连续空格切分，保留原始顺序；
  • 清理：去掉序号与首尾空白，括号内容单独保留为别名线索；
  • 去重：同名只保留第一次出现的位置（排位以第一次为准）；
  • 限长：超过 150 个成分时截断，并在报告里明确提示“只分析了前 150 个”。

输入框还会实时给出反馈：识别到几个成分、有没有可疑的空格缺失（整段没有分隔符时会提示“先检查一下分隔符”）， 让用户在点“开始解读”之前就知道这次输入是否可用。

5.2规则引擎：结论是怎么算出来的

维度规则输出
排位分档1–5 前段 / 6–10 中段 / 11 之后后段位置标签、含量级描述
概念添加功效成分排在后段，且不存在同功效的前段成分“更像是概念添加”提示
致敏风险香精、柠檬烯等香料致敏项 + 敏感肌档案高 / 中风险，进入“建议避开”或“需要留意”
孕期禁忌维 A 类（视黄醇等）、水杨酸高浓度等孕期档案下直接提示回避
刺激性表活类型、醇类、酸类与浓度相关字段刺激性提示，附使用建议
法规限量限用组分与最大允许浓度（成分库字段）法规提示，标记为“信息”而非风险
未收录不在成分库中的名称保留排位，标为未识别，进入占位

一个真实例子（报告里的第一条理由）：

柠檬烯 Limonene · 排位 13 / 14 · 敏感肌高风险
规则命中：香料致敏项（成分库）+ 排位后段 + 档案含敏感肌 → 风险等级 high → 结论“建议避开”。
模型只能说“它排在后段、含量很低，但致敏看的是有没有、不是多少”，不能提任何数字，也不能说“会过敏”。

规则输出是一个结构化对象：结论等级、headline、summary、flags（最多 3 条进主线）、sequence（完整配方顺序）、 matched / total。前端不需要理解规则，只负责按三段式渲染。

5.3报告：结论 / 理由 / 证据 三层

报告页的第一屏只有三样东西：一句结论、三条理由、一组数字。其余（配方梯队、法规、成分详情）折叠在后面。 这个结构的目的是把“我该不该用”和“为什么”放在同一屏，而把“完整信息”留给愿意深挖的人。

位置尺是报告里唯一的图形，也是产品的视觉主张：它把“排位”变成可读的空间关系 —— 左端是水，右端是千分之几，红点落在真实的冲突位置上。

证据层是第三层，也是最该被核对的一层：每条 AI 收录的成分，库里都多留了三样东西 —— 依据原句、模型自评置信度、研究时间与所用模型。打开成分详情就接在「别名」后面，像脚注一样短， 但足够回答“这句话凭什么”。

图 5-2　成分详情的「依据」区：依据原句 + 自评置信度 + 模型与时间，全部来自库里已有字段，不额外生成。
为什么非要写“模型自评”：这个数字没有校准过，也不是概率意义上的准确率。只写“置信度 82%”会让人把它当结论用， 所以界面上固定写「模型自评置信度」，并强制与「待人工复核」出现在一起 —— 两者缺一，就会变成另一种编造。

5.4流式渲染：前端怎么接

前端只有一个组件负责解释文本：StreamText.vue。它接收 url 与 payload， 自己建立 fetch 流，按四个事件类型更新状态：

  • 步骤条：把 step 事件渲染成三个 chip（读取规则结论 / 生成解释 / 数字与用语校验），完成变绿、进行中带脉冲；
  • 增量文本：delta 追加，末尾渲染一个光标，视觉上“正在写”；
  • 整段替换：replace 直接覆盖并切换来源标注；
  • 收尾：done 停止光标，若 source 是 template，则在下方显示一行小字说明原因。

中断控制用 AbortController：切换档案或离开页面时立即取消请求，避免旧解释覆盖新结论。 这也是流式应用最容易出的 bug —— 我们在档案重算时专门处理了竞态（用请求序号丢弃过期响应）。

5.5研究队列：边研究边收录，研究完再给结论

成分库只有几十条时，未收录是常态。处理方式不是让模型“猜”，也不是前端弹个错误，而是把未收录成分送进研究队列， 由研究 Agent 跑一遍完整流程（计划与决策见 4.4），把结果直接补进成分库，再让报告重新分析：

01
入队报告里出现的未收录成分写入研究任务（含原始片段与上下文）
02
Agent 研究归一化 → 查库 → 按需调模型 → 补角色 → 校验，全过程写 trace
03
自动收录字段合法就直接写入成分库（source=ai / status=pending），低置信度带标记与理由
04
报告重算前端每 6 秒轮询一次；新成分一旦入库，报告立刻按完整配方重算
05
可追溯 / 可复核管理台能看到每条任务的轨迹、置信度与依据，可改可删

5.5.1 研究没跑完，就不给结论

只要还有成分在队列里（researchQueued + researchRunning > 0），报告页不显示任何结论， 只显示一个进度页：已就绪 X / Y、正在查哪几个成分、一条进度条，以及一句「完成后自动显示结论，不用刷新」。 结论区、理由区、配方梯队、分享与打印按钮全部隐藏 —— 少一个成分就下的结论，不如不给。

研究完成后前端把报告整份替换掉，用户看到的是一次「从进度到结论」的切换，而不是先给一个半成品再改口。 如果研究 API 没配置（researchEnabled=false），进度页不会出现，报告照常显示并注明未收录成分未处理。

这条设计要解决的是信任问题：同一个成分表，研究前和研究后可能是两个结论。与其先给结论再偷偷改， 不如明确告诉用户「还在查，查完再告诉你」。收录的每一条都带来源与置信度，管理台随时可以推翻。

5.7前端设计系统（为什么它也算工程）

前端不是把数据摆上去就完事。为了让“结论层 / 理由层 / 证据层”这个信息结构稳定落地， 我们建了一套很小的设计系统：三色（纸 / 铜 / 墨绿）、八级字号、四个签名组件（透镜标、印章、位置尺、标本卡）。 规则只有一条：出现第九种字号或第四个断点，视为 bug。

这样做的直接收益是评审所说的“UI 设计与视觉表现”可被检验：换一个页面，颜色、字阶、间距不用重新决策； 而间接收益是交互一致 —— 报告页的“印章”与首页的“位置尺”是同一套语言，用户不会觉得是两个产品。

6.5性能：用户等的是哪一段

一次解读的时间其实分成三段：规则计算（毫秒级）、前端最小停留（约 0.7 秒）、模型首字（取决于上游）。 第二段是刻意的：后端通常几十毫秒就返回，如果让它瞬间出结论，用户会觉得“它根本没看”。 所以我们让步骤条至少走完一圈，让“规则在跑”这件事被看见 —— 这是交互设计，不是性能问题。

真正影响体验的是第三段。因为结论先渲染、解释异步追加，用户永远不会盯着空白页等模型： 最坏情况是结论已经在屏幕上，解释位置显示模板兜底。

Chapter 07

创新点说明

7.1技术创新点

T1　把“生成”关进“表达”的笼子：规则判结论、模型讲人话

主流做法是把成分表交给大模型，让它一次输出结论与解释。我们把两者拆开：结论由确定性规则产出， 模型只在“已有事实”上做语言组织。带来的直接结果是可复现（同一输入结论恒定）、 可测试（结论层可以单元测试）、可追责（错了能定位到规则还是模型）。 这不是“用了 AI”，而是“知道 AI 该用在哪一段”。

T2　流式解释的“断流检测 + 三级降级”

流式输出最容易被忽略的失败是“半句话当成功”。我们要求 finish_reason 正常 且 以句末标点收尾才算完整；否则走“非流式重试一次 → 仍失败则模板兜底”，并把原因显示给用户。 这条链路有专门的故障注入验证（截断、重试仍截断、输出含数字）。

T3　“无数字”排版：用相对量词替代浓度

输出闸门禁止任何数字与百分号，看似激进，实际逼出了一套更准确的表达：前段 / 中段 / 后段、 靠前 / 靠后、多数 / 少数。因为标签本身就不告诉消费者浓度，任何具体数字都只能是编的。 不写数字不是能力缺失，而是对信息边界的尊重。

T4　覆盖率先行：认不出就不下结论

当归档里的成分识别率低于 50% 且规则结论为“可以放心”时，系统主动降级为“信息不足”， 未识别成分以虚线占位保留原排位。绝大多数同类工具会把未知项直接忽略，从而给出一个错误的绿灯； 我们选择让“不知道”可见。

T5　位置尺：把“排位即含量”变成可读图形

法规的排位规则是公开知识，但从来没有被画出来。位置尺把 1–N 的排位映射到一条有刻度的轴上， 前 / 中 / 后三段分区，冲突项以红点落在真实位置。它同时用于首页讲原理、报告页标冲突、 设计系统做规范示例 —— 一个组件，三种用途。

T6　研究 Agent：把“要不要调模型”也变成可测试的决策

大多数“Agent”只是把模型调用包一层循环。这里相反：调不调模型是 Agent 判断出来的结果，不是流程规定。 命中成分库就直接结束（省一次调用、也避免模型改写已有条目）；需要核实时模型可以自己请求查库 / 查限量；字段不合法就换一种写法重问； 角色缺失先用词根规则补；置信度不够就交给人。每个分支都有单测，每一步都写进可回放的 trace， 而写库这一步永远在人的点击之后。

7.2应用创新点

A1　个体化重排：同一瓶东西，结论随人而变

切换“敏感肌”或“孕期”，同一份成分表的结论、理由、颜色都会变，并且界面会明确告诉你“哪一条变了、为什么变”。 这把“成分表解读”从一次性查询变成了可交互的决策工具。

A2　自动扩库：Agent 自己收录，但每一步都可追溯

未收录成分进入研究队列，Agent 跑完直接写入成分库并触发重算 —— 但每条都带来源、置信度、依据原文与完整轨迹， 管理台随时可以复核、修改或删除。自动收录解决的是「永远认不出新成分」的死循环，可追溯解决的是「收错了怎么办」。

A3　隐私优先的本地化：无账号、不出机

没有账号体系，没有服务端用户画像；成分表与档案存在本机，历史存在浏览器。 只有用户主动拍照时，图片才会发给已配置的视觉模型。这让产品可以被敏感肌、孕期人群放心使用。

Chapter 08

总结与展望

8.1做成了什么

成分镜完成了一条完整链路：粘贴或拍照 → 解析 → 规则判结论 → 个体化重排 → 模型写解释 → 闸门校验 → 三段式报告 → 分享 / 历史 / 成分库。在没有模型 Key、没有网络的情况下， 除了“解释的措辞”，其余功能全部可用。

更重要的是，我们把“AI 可能出错”这件事做成了产品的一部分：结论不靠模型、数字不靠模型、 未知不隐藏、失败有兜底、原因看得见。用户看到的不是“AI 说的”，而是“规则算的，AI 讲明白的”。

8.2局限

局限影响如果继续做
成分库只有几十条长尾成分经常未收录，覆盖率不足会频繁触发降级扩充到千级并用研究队列持续补录
只支持中文标签日文、英文成分表无法直接使用INCI 名称索引已具备，需补英文解析与同义词
单机 JSON 存储不适合多人同时使用，也无法做云端历史换成嵌入式数据库或服务端存储
规则表靠人工维护新法规、新成分需要人工更新建立法规条目版本化与变更提醒

8.3下一步

  1. 工具化（Function Calling / MCP）：把“查成分”“查限量”“提交研究”做成模型可调用的工具， 让解释阶段可以按需取证，而不是一次性拿到全部事实。
  2. 研究队列的 Agent 化：从“单条补全”升级为“自己发现缺什么、分批研究、带证据提交”， 但人工复核的角色从「入库闸门」变成「事后审计」。
  3. 端侧能力：用浏览器端小模型做初步分类，减少对上游的依赖，也让隐私叙事更彻底。
  4. 可评测性：建立标注集，持续统计“结论与皮肤科医生判断的一致率”“解释被闸门拦截的比例”， 把现在的“设计过的可控”变成“被数据证明的可控”。
一句话总结：我们做的不是一个“会聊成分的机器人”，而是一个“结论可核对、来源可追溯、认不出会明说”的成分解读工具。 AI 在其中负责它最擅长的部分 —— 把事实讲成人话。
