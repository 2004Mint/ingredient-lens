## 1. 五个最值得做（真实会咬人的）

### P-1 数据目录会随启动位置漂移 ← 部署必修

**证据**：7 个 Store 都用 `Paths.get(System.getProperty("user.dir"), "data")`（`AdminAuthService:31`、`AiSettingsStore:22`、`FeedbackStore:17`、`ReportStore:29`、`ResearchTaskStore:27`、`VisionSettingsStore:22`、`IngredientRepository:40`）。磁盘上已经分裂成两份：

| 目录 | 内容 | 状态 |
|---|---|---|
| `E:\AIWEB\data\` | ingredients.json **38 KB**、research-tasks.json 9 KB、ai-settings 693 B | 较新（10-31 05:52，含 AI 研究结果） |
| `E:\AIWEB\server\data\` | ingredients.json 17 KB、ai-settings 571 B | 较旧（10-31 01:36） |

也就是说：**在仓库根目录起 jar 和在 `server/` 下起，看到的是两套数据**。管理台里配的 Key、审核过的成分，换个目录启动就"消失"。

**改法**：抽一个 `DataPaths`（`@Value("${cosme.data-dir:}")` + 环境变量 `COSME_DATA_DIR`，默认 `${user.home}/.cosme/data` 或 jar 同级 `data/`），7 处改为注入；启动时打印解析后的绝对路径到日志。迁移时把两份 merge（以 38 KB 的为准）。
**工时** 0.5 天｜**收益**：避免线上"配置丢了"的诡异 bug；答辩被问"部署后数据在哪"能立刻答。

### P-2 `/api/analyze` 无入参上限、全站无限流 ← 公网必被刷

**证据**：`ApiController.analyze` 只校验"非空"；`AnalyzeService.analyze` 直接 `split(text)`，`MAX_TOKENS=150` 是切分**之后**才截断的；全仓无任何 rate limit / 并发闸门。而每次 analyze 都可能触发 `researchTasks.enqueue` → 消耗真实 API 额度。

**后果**：放公网演示的第一天，一个脚本 POST 10 MB 文本就能打满内存；或者刷 1000 次把 Key 额度烧光——**在线演示是加分项，也是最大的攻击面**。

**改法**：① 入参硬上限（文本 ≤ 6000 字符、图片 base64 ≤ 6 MB），超限返回 413 + 可读中文；② 轻量漏斗：每 IP 每分钟 20 次、同时在飞请求上限 8；③ 每 IP 每日研究任务上限（防止把队列刷满）。
**工时** 0.5 天｜**收益**：把"可选加分项"变成"敢公开放"。

### P-3 手机照片原图直传，不压缩 ← 体验与成本双输

**证据**：前端只有 `FileReader`，无 `canvas` 压缩；`VisionService.recognize` 直接把 base64 塞进 `data:image/...;base64,`。手机一张 8 MB 照片 → base64 约 11 MB JSON → 传给 VLM 时仍是大图，慢、贵、还容易触发上游 413。

**改法**：上传前 canvas 缩到长边 1600px、`toBlob('image/jpeg', 0.85)`，通常落到 300–500 KB；服务端再加一道兜底（超限拒绝并提示）。顺带把缩略图预览用压缩后的 blob，省内存。
**工时** 0.5 天｜**收益**：识别从"十几秒"降到几秒；同一张照片成本降一个量级；弱网可用。

### P-4 后端一挂，整站白屏 ← 答辩现场风险

**证据**：示例配方由 `GET /api/samples` 下发（`ApiController:98`），首页示例卡、`?sample=2/3` 全部依赖它；`web/src/lib/http.js` 失败时只会抛"连不上本机后端（8082）"。README 写的"三个示例配方，无网络也能完整演示"实际含义是"不需要 AI Key"，**断网/后端未起时什么都看不到**。

**改法**：把 3 个示例的 `samples` + 预生成好的 `report` JSON 作为静态资源放进 `web/public/demo/`；`/api/samples` 失败时自动回退到静态数据。这样"断网答辩"也能完整跑一遍报告页（只读）。
**工时** 0.5 天｜**收益**：答辩最怕的"现场网不好/服务没起"直接免疫；也让"离线演示"这句宣传变成真的。

### P-5 「宣称核验」——把选题洞察再往前推一步 ← 差异化最强

**证据**：现在的核心能力是"排位 → 含量梯队 → 概念添加"，但用户真正的困惑是"**广告说的和成分表说的是一回事吗**"。产品已经有 `claims` 的位置（示例卡里硬编码了"主打烟酰胺美白，但烟酰胺排在很后面"这类文案），却没有把"宣称 → 成分 → 排位"做成可交互的推理。

**改法**：输入时允许选/填宣称（美白、抗老、敏感肌可用、控油…）；规则侧建一张 `claim → 责任成分` 映射（烟酰胺/VC/377→美白，视黄醇/胜肽→抗老，神经酰胺/泛醇→屏障）；输出三档结论：**有支撑 / 概念添加（有成分但排位靠后）/ 无对应成分**。每条结论挂 `ruleId` + 依据。
**工时** 1.5–2 天｜**收益**：直接命中"选题创新 10%"和"解决方案有效性 5%"；演示时一句"这瓶宣称美白，但美白成分排第 12 位，属于概念添加"比任何架构图都有说服力。

## 3. 一小时能做完的（quick wins）

1. `.gitignore` 是 GBK 编码（唯一非 UTF-8 文件），GitHub 上注释全是乱码 → 转 UTF-8。
2. `/api/analyze` 文本上限 6000 字符（`ApiController:118` 三行）。
3. 错误信息脱敏：`"分析失败：" + e.getMessage()` → 通用文案 + 日志。
4. 图片 base64 服务端上限 6 MB（`ApiController:168` 一行）。
5. README 里"PWA"改成"PWA 清单（manifest）"，别让评委发现名不副实。
6. `package.json` 加 `"lint"` / `"typecheck"` 脚本占位（即使暂未接工具）。
